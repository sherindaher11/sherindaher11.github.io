NVIDIA / Run:ai

Open-Source Documentation Transformation

Redesigning an enterprise documentation ecosystem for an open-source platform and a new developer and contributor audience.

Role
Technical Marketing Engineer / Documentation Lead
Focus
Documentation Strategy · Open Source · Developer Experience · Information Architecture · Docs-as-Code

Context

Run:ai is an AI infrastructure platform for orchestrating and managing AI workloads. As the platform prepared to transition to open source, its documentation needed to evolve from an enterprise-focused model to support developers and open-source contributors as well as existing product users.

This was not a simple content migration. The transition required rethinking how people discover the project, understand the platform and its architecture, move between GitHub and the documentation site, and contribute documentation alongside source code.

The Challenge

The existing documentation had primarily been designed around product users and administrators. Open sourcing the platform introduced new audiences, entry points, contribution patterns, and expectations.

  • Create a clear path from project discovery to understanding and using the platform.
  • Provide architecture and service-level documentation for developers working with the source.
  • Make GitHub a meaningful documentation entry point rather than simply a code repository.
  • Preserve task-oriented product documentation for operators and end users.
  • Enable engineers and external contributors to contribute through familiar Git-based workflows.
  • Establish standards and review processes that could scale beyond a single documentation owner.
  • Prioritize launch-critical work without turning the transition into an unrealistic rewrite of the entire documentation set.

My Role

As the documentation owner for Run:ai, I defined the documentation transformation strategy for the open-source transition and led its implementation in partnership with Engineering, Product, and other stakeholders.

  • Assessed the existing documentation against developer and open-source contributor personas.
  • Identified content, architecture, workflow, and contribution gaps.
  • Developed a phased P0/P1/P2 roadmap separating launch-critical work from longer-term improvements.
  • Designed the documentation architecture across GitHub, the product repository, and the documentation site.
  • Defined information architecture, content responsibilities, standards, and contribution patterns.
  • Led the move into the product monorepo and a docs-as-code workflow.
  • Worked with Engineering and Product to validate technical structure, terminology, workflows, and documentation requirements.

Approach

01

Start With the New Audience

I assessed the existing documentation against the needs of the open-source audience rather than treating the project as a direct migration. The assessment considered product users, operators, developers, and contributors and identified where the existing model did not adequately support project discovery, architecture understanding, source-level exploration, or contribution.

02

Define a Layered Documentation Architecture

I designed a model in which different types of documentation live where users and contributors naturally expect to find them.

  • Root README: project introduction, high-level architecture, quick start, build-from-source guidance, contributing, community, and license.
  • Architecture documentation: deeper explanation of how the platform and services fit together.
  • Service READMEs: responsibilities, repository structure, and build/run/test/extend guidance.
  • Concepts: platform domain objects and relationships.
  • Tasks: workflows for using and operating the platform.
  • Reference: API, CLI, YAML, CRD, and related technical reference material.
GitHub / Repository Documentation Site Root README Concepts ↓ ↓ Architecture ←──────────────→ Tasks ↓ ↓ Service READMEs Reference

The goal was not to move all documentation into GitHub. It was to create a deliberate relationship between repository-level developer documentation and the broader product documentation experience.

03

Prioritize the Transformation

I used a P0/P1/P2 roadmap to distinguish the launch foundation from subsequent improvements.

P0 Launch foundation → P1 IA & developer content → P2 Continued expansion

P0 covered the platform and publishing foundation, core entry points, getting-started and installation content, repository documentation, and foundational developer material. P1 expanded information architecture and concept/developer content. P2 created a path for continued refinement as the open-source experience matured.

04

Integrate Documentation With Development

Documentation moved into the product monorepo and became part of the same Git-based development environment used by engineering teams.

Product change → Documentation change → Pull request → Review → Preview → Publish

The workflow incorporated source control, pull requests, documentation review, CI-generated previews, automated publishing, engineering contribution, and defined standards.

Outcome

The transformation established a documentation foundation designed for an open-source product rather than simply repackaging the existing enterprise documentation.

  • Documentation became part of the product repository and development workflow.
  • GitHub became a deliberate entry point into the documentation experience.
  • Repository, architecture, service, concept, task, and reference content gained clearer roles.
  • Documentation contribution became compatible with standard Git and pull-request workflows.
  • CI previews and automated publishing supported review before publication.
  • The phased roadmap provided a practical path for continuing the transformation after launch.
