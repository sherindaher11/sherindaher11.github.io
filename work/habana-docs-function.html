Habana Labs (Intel)

Building a Documentation Function From Zero

Building the documentation infrastructure, processes, content architecture, and team for a growing AI software platform.

Role
Senior Technical Writer / Team Lead
Focus
Documentation Strategy · Infrastructure · Docs-as-Code · Information Architecture · Engineering Contribution · Team Building

Context

I joined Habana Labs as its first technical writer while the company was building and scaling its AI software platform.

Documentation existed, but there was not yet a mature documentation function or scalable infrastructure. As the platform and engineering organization grew, documentation needed to evolve from individually produced files into a structured system that could support frequent software releases, increasingly complex technical content, engineering collaboration, and a growing documentation team.

The assignment therefore went beyond writing product documentation. It required building the function behind it.

The Challenge

The challenge was to establish a documentation capability that could scale with a rapidly evolving AI software platform.

  • Move away from document-centric Word-based authoring.
  • Establish source-controlled authoring and publishing workflows.
  • Select and implement documentation tooling appropriate for technical software content.
  • Create scalable information architecture, standards, and review processes.
  • Support a six-week software release cadence.
  • Create structured ways for engineers and technical contributors to participate.
  • Document complex workflows spanning installation, configuration, APIs, AI frameworks, containers, orchestration, distributed workloads, debugging, and optimization.
  • Grow documentation capacity beyond a single technical writer.

My Role

As the first technical writer, I established the documentation function while also owning documentation delivery for the platform.

  • Assessed the existing documentation environment and identified infrastructure and process gaps.
  • Evaluated and implemented a docs-as-code approach.
  • Migrated documentation from Word-based authoring to Sphinx and Read the Docs.
  • Established source-controlled authoring and publishing workflows.
  • Restructured information architecture around user workflows.
  • Established documentation standards, reviews, and release processes.
  • Partnered with R&D, Product Management, Application Engineering, and Marketing on technical content.
  • Created contributor workflows and trained engineers and technical contributors.
  • Recruited and trained two additional technical writers.
  • Managed documentation delivery alongside the six-week software release cadence.

Approach

01

Build the Documentation Infrastructure

I evaluated tooling and moved the organization from Word-based documentation toward a docs-as-code model using Sphinx and Read the Docs. The new model introduced source control, structured text-based authoring, repeatable publishing, and a foundation that could support contributions from multiple authors.

Word-based documents → Source-controlled content → Sphinx → Review → Read the Docs

The objective was not simply to replace one authoring tool with another. It was to establish documentation as a maintainable technical system.

02

Restructure Around User Workflows

As the platform expanded, documentation needed to help users complete workflows that crossed multiple technical layers rather than mirror the internal organization of individual components.

I reworked the information architecture around installation and configuration, APIs, PyTorch training and inference, Docker and Kubernetes environments, distributed workloads, debugging, performance optimization, and developer workflows.

This created a more coherent experience across software, hardware, APIs, orchestration, and AI development.

03

Establish Contribution and Governance

Scaling documentation required reducing dependency on a single documentation owner while maintaining quality and consistency. I established standards, authoring guidance, review processes, contributor workflows, and training for engineers and other technical contributors.

Engineering / Technical Contributors → Documentation Workflow → Review → Published Documentation
04

Scale the Function, Not Just the Content

I recruited and trained two additional technical writers and established processes that allowed documentation work to be distributed while maintaining common standards and release expectations.

Documentation delivery was coordinated with the six-week software release cadence through ongoing collaboration with R&D, Product Management, Application Engineering, and Marketing.

Outcome

The result was a documentation capability supported by infrastructure, processes, contributors, and a growing team rather than a collection of individually maintained documents.

  • Documentation moved from Word-based authoring to Sphinx and Read the Docs.
  • Content became source controlled with repeatable publishing workflows.
  • Information architecture was reorganized around technical user workflows.
  • Documentation standards and review processes were established.
  • Engineers and technical contributors gained structured contribution paths.
  • Documentation delivery became integrated with the software release cadence.
  • The function expanded from the first technical writer to a multi-writer team.
