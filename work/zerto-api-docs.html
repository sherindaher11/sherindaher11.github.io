Zerto

API Documentation & Technical Validation

Combining API documentation with hands-on validation to ensure developer-facing content reflected actual product behavior.

Role
Senior Technical Writer
Focus
API Documentation · Technical Validation · Postman · Information Architecture · Engineering Collaboration

Context

At Zerto, I documented public-cloud features, technical workflows, and APIs for a disaster recovery and cloud data management platform.

API documentation required more than translating engineering input into reference content. Developer-facing examples and descriptions needed to match the behavior users would encounter when making actual requests.

The Challenge

The documentation needed to explain API behavior accurately while remaining usable for developers implementing integrations.

  • Validate calls rather than relying only on source material.
  • Confirm requests and responses against actual behavior.
  • Resolve discrepancies through collaboration with Engineering and QA.
  • Translate validated behavior into clear developer-facing documentation.
  • Improve information architecture and usability around complex technical workflows.

My Role

I created and maintained API and technical documentation while working directly with Engineering and QA to validate behavior.

  • Used Postman hands-on to test API calls.
  • Reviewed requests and responses against documented behavior.
  • Worked with Engineering and QA when validation surfaced discrepancies or ambiguity.
  • Converted verified behavior into reference and workflow documentation.
  • Contributed to information architecture, usability, tooling, and publishing improvements.

Approach

01

Start With the Developer Task

I approached API content from the implementation path a developer needed to follow, connecting reference information with the broader product workflow rather than treating endpoints as isolated descriptions.

02

Validate With the Product

I used Postman to exercise API calls and inspect requests and responses. This provided a practical check that developer-facing documentation matched the behavior users would encounter.

Engineering Input → API Call in Postman → Validate Request / Response → Resolve Gaps → Documentation
03

Resolve Ambiguity Collaboratively

When observed behavior and available information did not align, I worked with Engineering and QA to clarify expected behavior before publishing it as authoritative documentation.

What It Demonstrates

This work reflects an approach I continue to use in developer documentation: technical content should be validated against the product wherever possible, not treated as a purely editorial deliverable.

  • Hands-on API validation using Postman.
  • Close collaboration with Engineering and QA.
  • Developer-oriented information architecture.
  • Translation of complex behavior into usable technical documentation.
